# Acceptance Criteria: All Requirements

## Functional Requirements

| ID | Requirement | Acceptance Criteria |
|:--|:--|:--|
| FR-01 | The system shall accept a path to a single .log or .txt file, or to a directory, as a command-line argument. | Given a valid file path, when the scan is run, then every line is read and processed without error. Given a directory path, when the scan is run, then the supported files inside it are scanned. |
| FR-02a | The system shall detect email addresses matching the standard format (local-part@domain). | Given a file containing a known valid email address, when the file is scanned, then it is reported as an "Email" finding with the correct line number. |
| FR-02b | The system shall detect phone numbers with 10 digits in total, with an optional country code. | Given a file containing a known valid phone number such as +1 (555) 123-4567, when the file is scanned, then it is reported as a "Phone" finding with the correct line number, and it is not also reported as a credit card on the same line. |
| FR-03a | The system shall detect AWS Access Key IDs starting with AKIA, ASIA, AROA or AIDA, followed by 16 letters or digits. | Given a file containing a key with one of these prefixes, when the file is scanned, then it is reported as an "AWS Access Key ID" finding. |
| FR-03b | The system shall detect password or secret assignments using the keywords password, passwd, pwd or secret, followed by a colon or equals sign and a value of at least 4 characters. | Given a line such as `password = value` or `pwd: value`, when the file is scanned, then it is reported as a "Password assignment" finding containing only the value, not the keyword. Given a value shorter than 4 characters, then it is not reported. |
| FR-03c | The system shall detect PEM-format private key blocks, from a 'BEGIN PRIVATE KEY' header to its matching 'END PRIVATE KEY' footer, with a maximum of 100 lines in between. | Given a block with both header and footer within 100 lines, when the file is scanned, then the whole block is reported as one "Private Key Block" finding at the header's line number. Given a header with no footer, then the behaviour is defined and tested (see DEF-009). |
| FR-03d | The system shall detect MD5, SHA1 and SHA256 hash values based on their fixed hexadecimal length (32, 40 and 64 characters). | Given a 32, 40 or 64 character hexadecimal string, when the file is scanned, then it is reported as an "MD5 Hash", "SHA1 Hash" or "SHA256 Hash" finding respectively. |
| FR-03e | The system shall detect Base64-like tokens made of two parts of at least 20 letters, digits, hyphens or underscores, separated by a full stop. | Given a token in this format, when the file is scanned, then it is reported as a "Base64-like token" finding. |
| FR-04 | The system shall produce a Risk Report showing what was found, where (line number) and what type of finding it is. | Given a scan with findings, when the scan completes, then each finding is shown with its line number and pattern name in the console and the report. |
| FR-05 | Findings in the console and report output shall be masked as specified in FR-08. The system shall never display or save an unmasked finding. | Given any finding, when it is displayed or saved, then no unmasked value appears in the console output or the report file. |
| FR-06 | The system shall reject a missing file with a FileNotFoundException, and a file that is not .log or .txt with an ArgumentException, each with a clear error message. | Given a path that does not exist, when a scan is attempted, then a FileNotFoundException is thrown with the message "File not found". Given an existing file that is not .txt or .log, then an ArgumentException is thrown stating the file type is invalid. |
| FR-07 | The system shall write a report file when --out is given. The report has a header (scanned path, timestamp, finding count) and one line per finding with the line number, pattern name and masked value, plus the file path when a directory is scanned. | Given the `--out` argument, when the scan completes, then a report file is created with the header and one masked line per finding. Given a directory scan, then each line also includes the file path. |
| FR-08 | The system shall mask every finding before it is displayed or saved, so only the first 4 and last 4 characters are visible. Values of 8 characters or fewer shall be fully masked. | Given a value longer than 8 characters, then only its first 4 and last 4 characters are visible and the middle is replaced by asterisks. Given a value of 8 characters or fewer, then it is fully replaced by asterisks. |
| FR-09 | The system shall report a credit card number only if it is 13 to 19 digits long and passes the Luhn checksum. | Given a 13 to 19 digit sequence that passes the Luhn checksum, when the file is scanned, then it is reported as a "Credit Card (possible)" finding. Given a sequence that fails the checksum, then it is not reported. |
| FR-10 | When given a directory, the system shall scan all .log and .txt files in it, including files in nested subdirectories. | Given a directory containing supported files at several levels, when the directory is scanned, then every supported file is scanned and its findings are returned. |
| FR-11 | When scanning a directory, the system shall skip files and folders excluded by the .gitignore in the root of that directory. Nested .gitignore files are not read. If there is no .gitignore, all supported files are scanned. | Given a file or folder listed in the root .gitignore, when the directory is scanned, then it is not scanned and its secrets are not reported. Files not listed are still scanned. |
| FR-12 | When scanning a directory, the system shall skip files that are not .log or .txt, print a message for each skipped file, and not return them in the results. | Given a directory containing .md, .json or .dll files, when it is scanned, then they are not returned in the results and a skip message is printed for each. |
| FR-13 | If a file cannot be read during a directory scan, the system shall print an error message for that file and continue with the next file. | Given one unreadable file and one readable file in a directory, when it is scanned, then an error message is printed for the unreadable file and the readable file's findings are still returned. |

## Non-Functional Requirements

| ID | Requirement | Acceptance Criteria |
|:--|:--|:--|
| NFR-01 | The system shall process a log file up to 10MB within 5 seconds. | Given a log file of about 10MB, when a scan is run and timed, then it completes in 5 seconds or less. |
| NFR-02 | The system shall detect 100% (10 of 10) of the findings planted in the Secrets.log test file, with the correct pattern name and line number for each. | Given Secrets.log, when it is scanned, then exactly 10 findings are returned, each with the expected pattern name, value and line number. |
| NFR-03 | The system shall never send scanned files or findings anywhere externally. | Given a scan is run, then no outbound network requests are made. Checked by code inspection, because the code contains no network calls. |
| NFR-04 | The system shall run as a command-line tool that developers can invoke manually, returning a non-zero exit code when secrets or PII are found, so the scan result can block a git push. | Given a scan finds one or more findings, when the tool finishes, then it returns a non-zero exit code. Given no findings, then it returns zero. |
| NFR-05 | The detection logic (regex patterns, Luhn validation and masking) shall be kept in separate classes from the command-line entry point and directory scanning, so rules can be updated on their own. | Given a new pattern is added to `SecretsScanner.Patterns`, then no change is needed in `Program.cs` for it to take effect. |
| NFR-06 | The system shall run on Windows without needing extra paid tools or accounts. | Given a Windows machine with only .NET installed, when the tool is built and run, then it works with no extra paid software or sign-ups. |
| NFR-07 | The system shall not keep or log the contents of scanned files after the run ends, unless the user exports a report. | Given a scan is run without `--out`, when the process exits, then no file containing scanned content or findings is left on disk. |
